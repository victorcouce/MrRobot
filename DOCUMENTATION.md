# MrRobot — Complete Technical Documentation

> Multi-agent orchestrator for software development. It takes a high-level
> goal, breaks it down into a DAG of tasks, runs them with **Codex / Claude /
> DeepSeek** in **isolated Git worktrees**, reviews and validates the result,
> and leaves all the work on an **isolated Git branch** (it never merges into
> `main`).

This document describes **what it is**, **all of its features** and **every
possible flow** (backend, API, CLI, UI, states, errors and recovery).

## 1. What MrRobot is

MrRobot is a **multi-agent engine in TypeScript** that orchestrates several
LLMs to build software autonomously from a natural-language description.

Given a **goal** (e.g. *"Create a TypeScript library with `sum(a,b)`, tests and
a README"*), the engine:

1. **Plans**: a planner LLM breaks the goal down into a **DAG of tasks** (with
   dependencies, type, complexity and acceptance criteria).
2. **Validates** the DAG (unique IDs, existing dependencies, no cycles).
3. **Runs** the tasks in parallel (with a concurrency limit) while respecting
   dependencies, each one **isolated in a Git worktree**.
4. **Picks the best agent** by type/complexity and **falls back** to other
   models if one fails, runs out of quota or hits its limit.
5. **Reviews** every task (local checks + LLM reviewer) and **retries it with
   feedback** if it does not meet the criteria.
6. **Supervises** the overall result and decides `continue | replan | pause | fail`.
7. **Finalizes** by integrating all commits into an **isolated branch**
   (`agent/project-<id>-final`), optionally with a **push** to the remote.

### Design philosophy

- **No extra token cost**: Codex and Claude authenticate with your **regular
  subscription** (ChatGPT Plus/Pro, Claude). LM Studio runs models locally, at
  no cost. DeepSeek is the only provider that requires `DEEPSEEK_API_KEY`
  (paid).
- **Never destructive**: the engine **never** merges into `main`/`master` nor
  touches the main working tree. Everything happens in isolated worktrees and
  branches.
- **Backend as the single source of truth**: the UI rebuilds its state from the
  API; pressing `F5` in the middle of a run loses nothing.
- **Fail-safe**: planner/reviewer/supervisor validate their output with Zod; on
  invalid responses the engine retries or safely continues.

## 2. Key concepts

| Term | Meaning |
|---|---|
| **Project** | High-level entity with a goal, a DAG of tasks and a status. |
| **Task** | Atomic unit of work with `type`, `complexity`, `dependsOn`, `acceptanceCriteria`. |
| **Plan / DAG** | Directed acyclic graph of tasks generated by the planner. |
| **Agent** | A specific provider + model: `codex`, `claude/sonnet`, `claude/opus`, `claude/haiku`, `deepseek-flash`, `deepseek-v4-pro`. |
| **Fallback chain** | Ordered list of candidate agents for a task. |
| **Worktree** | Isolated Git working copy (`.worktrees/...`) per task attempt. |
| **Attempt** | One specific try by an agent at a task. |
| **Review** | Verdict of the LLM reviewer (approved / rejected + issues). |
| **Check** | Local script (`npm run typecheck/build/test`) run against the result. |
| **Supervisor** | Agent that decides whether to continue, replan, pause or fail. |
| **Chat** | Per-project conversation thread that generates/adjusts tasks via the planner. |
| **Preview** | Development server of the completed project, started in a worktree. |
| **Event log** | Append-only record of everything that happens in the project. |

## 3. Architecture

```text
UI (ui/ — Next.js App Router)
 ↓  HTTP + SSE
API (src/api — thin HTTP layer, Node http)
 ↓
Project service (src/projects)  +  Chats (src/chats)  +  Preview (src/preview)
 ↓
LangGraph (src/graph)         planner → run → supervise → finalize
 ↓
Planner / Scheduler / Supervisor (src/planner, src/scheduler, src/supervisor)
 ↓
Tasks (src/tasks)             runTask: retries + fallbacks + worktrees
 ↓
Agent Router (src/agents)     selectAgent + getFallbackChain + runAgent
 ↓
Codex / Claude / DeepSeek (src/providers)
 ↓
Git worktrees (src/workspace)
 ↓
Storage (src/storage)         PGlite (Postgres) or memory
```

Architecture principles:

- The **UI never** calls Codex/Claude/DeepSeek, Git, worktrees or PostgreSQL
  directly. Everything goes through the **HTTP API** (`src/api`).
- The **route handlers** contain no domain logic: they delegate to
  `projects/service.ts`, `projects/plan-editor.ts`, `chats/service.ts`, etc.
- The **wire types** are shared in `shared/types.ts` between backend and UI.

### Module map

| Module | Responsibility |
|---|---|
| `providers/` | Run CLIs/APIs: `runCodex`, `runClaude`, `runDeepSeek`. |
| `agents/` | `selectAgent`, `getFallbackChain`, `isRetryableError`, `AgentHealth`, `runAgent`. |
| `tasks/` | `runTask`: retries per agent + fallback between agents, each attempt in a clean worktree. |
| `scheduler/` | Validates the DAG and runs it in parallel with a concurrency limit. |
| `workspace/` | Worktrees, commits, dependency cherry-picks and the final branch. |
| `planner/` | Generates the DAG (output validated with Zod). |
| `reviewer/` | Reviews tasks against their acceptance criteria. |
| `supervisor/` | Decides `continue | replan | pause | fail`. |
| `projects/` | Project entity and orchestration (create/plan/run/pause/resume). |
| `chats/` | Per-project conversation threads; every message goes through the planner. |
| `storage/` | Persistence (PGlite/memory) + event log. |
| `checks/` | Detection and execution of local verification scripts. |
| `preview/` | Starts the completed project's development server. |
| `graph/` | LangGraph graph that orchestrates planner/scheduler/supervisor. |
| `api/` | HTTP server, runtime, serialization, parsing, mock. |
| `cli/` | Terminal commands. |

## 4. Requirements and installation

### Basic requirements

- **Node.js 20+** and **npm**
- **git**

### To run real tasks (non-mock)

The engine invokes the `codex` and `claude` CLIs directly, so they must be
installed, on the `PATH`, and authenticated once:

```bash
# Codex CLI — codex provider (complex coding tasks)
npm install -g @openai/codex
codex login

# Claude Code CLI — planner, reviewer, supervisor and tasks
npm install -g @anthropic-ai/claude-code
claude          # the first run opens the authentication flow
```

- **DeepSeek** works over HTTP; it needs no CLI, only `DEEPSEEK_API_KEY`.
- **LM Studio** works over HTTP against a local model; it needs no CLI or key,
  only the local server running (`http://localhost:1234/v1` by default,
  configurable with `LMSTUDIO_BASE_URL`).

> **You do not need to buy tokens or a separate paid API.** Codex and Claude
> use your regular ChatGPT / Claude subscription. LM Studio runs locally at no
> cost. The only provider with a paid API key is DeepSeek.

If you just want to try it without spending tokens, use **mock mode** (see §27);
you don't need to install or authenticate anything.

### Installation

```bash
npm install                     # backend
cd ui && npm install && cd ..   # graphical interface
```

## 6. Configuration

Central configuration lives in `src/config/index.ts` (`loadConfig`, `mergeConfig`).

### Default values (`defaultConfig`)

```ts
{
  concurrency: 3,             // initial concurrency
  maxConcurrency: 6,          // ceiling for adaptive concurrency
  maxRetriesPerAgent: 1,      // retries per agent (=> up to 2 attempts)
  maxReviewFixCycles: 2,      // review/fix cycles (=> up to 3 executions)
  plannerMaxAttempts: 2,      // planner attempts to get a valid plan
  limitRetry: {               // retry of the whole chain when limits are exhausted
    maxLimitRetries: 3,       //   times the chain is walked again
    baseDelayMs: 30000,       //   base wait if there is no "retry after"
    maxDelayMs: 900000,       //   wait ceiling (15 min)
  },
  checks: { commands: [] },   // [] => autodetect npm scripts
  defaultAllowedAgents: [],   // [] => no restriction (the user picks them in the chat)
}
```

There are no fixed agents per role. The user chooses the set of allowed agents
when launching the first chat prompt; the engine selects the agent by type and
complexity (`selectAgent`/`getFallbackChain`) both for tasks and for the
orchestration roles (planner, reviewer, supervisor, grill and instructions)
through `runRoleAgent` (`src/agents/role.ts`).

- `loadConfig(overrides)`: `{ ...defaultConfig, ...overrides, checks: { ...defaultConfig.checks, ...overrides.checks } }`.
- `mergeConfig(base, overrides)`: same, but starting from `base`.
- `fallbackCodingAgent = { provider: "claude", model: "haiku" }`.

### Per-project config

A project can override the global config:

- When it is created (*New Project* screen, advanced section) or via
  `POST /api/projects` with the `config` field.
- Afterwards, via `PATCH /api/projects/:id/config` **while it is in `draft`,
  `ready` or `paused`**.

On the first change, the project **materializes its own config** (it stops
inheriting from the global one). If it defines no config, it uses the global one.

> Implementation note: `createProject` (non-draft) **does not persist**
> `input.config`; `createProjectDraft` **does**. In the API, the runtime applies
> the config overrides when creating the project.

## 9. Providers and agents

### 9.1 Providers (how each model is invoked)

| Provider | Implementation | Invocation |
|---|---|---|
| **Codex** | `src/providers/codex.ts` | `codex exec --sandbox workspace-write <prompt>` (CLI, no shell). |
| **Claude** | `src/providers/claude.ts` | `claude -p <prompt> --permission-mode acceptEdits` + `--model sonnet|opus` if a model is given. Read-only roles (planner, reviewer, supervisor) run without `--permission-mode`. |
| **DeepSeek** | `src/providers/deepseek.ts` | HTTP with the `openai` SDK pointed at `https://api.deepseek.com`; `chat.completions.create` with a single user message. Default model `deepseek-flash`. |

Details of `execCli` (`src/providers/exec.ts`):

- Uses `child_process.spawn` (no shell) and **emits stdout/stderr live** through
  `RunOptions.onOutput`, accumulating up to 10 MiB.
- Supports `cwd` (worktree) and `AbortSignal` (cancellation).
- After spawning it calls `stdin.end()` because some CLIs (Codex) wait for EOF
  even when the prompt is passed as an argument.
- On failure: `[<provider>] falló la ejecución (exit code: <code>): <stderr|stdout|message>`.
- DeepSeek accepts **neither** `cwd`/`signal` nor streaming (it supports neither
  worktree isolation nor process cancellation; it stops at the end of the batch).

### 9.2 Agent selection (`selectAgent`)

Deterministic selection by `type` and `complexity` (the explicit `task.agent`
always wins, via `resolveAgent`):

| Type | low | medium | high | critical |
|---|---|---|---|---|
| `architecture` | Opus | Opus | Opus | Opus |
| `planning` | Opus | Opus | Opus | Opus |
| `coding` | Haiku | Haiku | Haiku | Haiku |
| `review` | Sonnet | Sonnet | Opus | Opus |
| `testing` | Haiku | Haiku | Haiku | Haiku |
| `research` | DeepSeek Flash | Sonnet | Opus | Opus |

Planning and architecture always go to Opus (the most capable model); already
planned development (`coding` and `testing`) is handled by Haiku. `review` and
`research` keep their split by complexity.

`describeAgent`: `codex` → `"codex"`; everything else → `"<provider> / <model>"`
(e.g. `"claude / opus"`).

### 9.3 Fallback chain (`getFallbackChain`)

Each chain has **3 candidates**. If the task defines `task.agent`, it is
**prepended** and the list is deduplicated by the `provider:model` key.

| Type | Complexity | Chain |
|---|---|---|
| `architecture` | all | Opus → Codex → Sonnet |
| `planning` | all | Opus → Codex → Sonnet |
| `review` | high/critical | Opus → Codex → Sonnet |
| `review` | the rest | Sonnet → Codex → DeepSeek Flash |
| `coding` | all | Haiku → Sonnet → Codex |
| `testing` | all | Haiku → Sonnet → Codex |
| `research` | low | DeepSeek Flash → Sonnet → Opus |
| `research` | medium | Sonnet → DeepSeek Flash → Opus |
| `research` | high/critical | Opus → Sonnet → DeepSeek Flash |

Guaranteed invariant: `getFallbackChain(task)[0]` is always `selectAgent(task)`
(when there is no explicit agent).

The chain is **restricted to the allowed agents** of the chat/project
(`restrictToAllowed`); an empty list means "no restriction". The orchestration
roles reuse these same chains by mapping role → task type (`runRoleAgent`,
`src/agents/role.ts`): planner/supervisor/instructions → `planning`, reviewer →
`review`, grill → `research`.

### 9.4 Error classification and availability

**Retryable** (`isRetryableError`): it first rules out anything matching a
**non-retryable** pattern; otherwise, it is retryable only if it matches a
retryable pattern.

- **Non-retryable**: `api key`, `apikey`, `unauthorized`, `forbidden`, `401`,
  `403`, `not found`, `enoent`, `command not found`, `invalid model`,
  `unknown model`, `invalid_request`, `invalid request`, `400`.
- **Retryable**: `timeout`, `timed out`, `etimedout`, `econnreset`,
  `econnrefused`, `enotfound`, `eai_again`, `network`, `connection`,
  `disconnected`, `socket hang up`, `rate limit`, `rate_limit`,
  `too many requests`, `429`, `500`, `502`, `503`, `504`, `internal server error`,
  `service unavailable`, `bad gateway`, `gateway timeout`, `temporarily`,
  `temporary`, `unavailable`, `overloaded`, `try again`, `terminated`, `killed`,
  `sigterm`, `sigkill`.

> Quota/session limits (`session limit`, `usage limit`, `quota`,
> `insufficient_quota`, `out of credits`) are in **neither** list, so they are
> treated as non-retryable and cause an **immediate jump** to the next agent in
> the chain.

**Chain retry when limits are exhausted** (`src/agents/limit-retry.ts`): if
*no* candidate could run because **all** of them fell over on a limit
(`rate_limit`/`usage_limit`), `runTask` and `runRoleAgent` do not give up: they
wait (honoring a provider's `retry after N` if present, or an exponential
backoff) and walk the whole chain again up to `limitRetry.maxLimitRetries`. A
transient failure or one of another kind disables this retry (the chain is not
walked again). The wait can be cancelled with `AbortSignal`.

**Availability** (`classifyAvailability`, `src/agents/availability.ts`):
classifies into `usage_limit | rate_limit | auth | cli_missing | network | unknown`
according to an order of precedence. It is wired into execution: when a provider
is unavailable, `runTask` and `runRoleAgent` **jump to the next candidate without
retrying it** (this takes priority over `isRetryableError`); if all fall over on
a limit, the chain retry described above applies. The API additionally uses
`checkAgentAvailability` to expose each provider's status to the UI.

**Quarantine of exhausted agents** (`AgentHealth`, `src/agents/health.ts`): the
chain retry above applies to *one* task, but the engine must not start over with
a provider that has just run out. `runTask` and `runRoleAgent` accept an optional
`agentHealth`: when a candidate falls over on `rate_limit`/`usage_limit`, it is
marked and `order()` moves it to the end of the chain in subsequent executions,
so work continues with the agent that worked. The quarantine lasts the
provider's `retry after` or, if there is none, `cooldownMs` (5 min by default),
capped at `maxCooldownMs` (1 h); `recordSuccess` lifts it if the agent responds
again. It does not remove candidates: the exhausted one remains the last resort.
The server's `Runtime` shares a single instance across rounds and projects
(`ProjectDeps.agentHealth`); without it, the order of `getFallbackChain` does not
change.

**Agent availability in the API** (`src/api/availability.ts`):

- `codex --version` and `claude --version` (5 s timeout) → connected if the
  binary exists (even if it exits with a code ≠ 0); `ENOENT` → not connected
  with reason `CLI "<command>" no encontrado en el PATH.`
- DeepSeek: connected if `DEEPSEEK_API_KEY` is defined; otherwise reason
  `"DEEPSEEK_API_KEY no está definida."`
- LM Studio: connected if `GET <LMSTUDIO_BASE_URL>/models` responds 2xx (3 s
  timeout, `http://localhost:1234/v1` by default); otherwise reason
  `"No se pudo conectar con LM Studio en <url>."` or the status code received.

## 10. Planner (goal decomposition)

`src/planner/planner.ts` — `planProject(goal, context?, deps?)`.

- **Agent**: chosen by complexity and restricted to the project's/chat's allowed
  agents, with a fallback chain by availability (`runRoleAgent`).
- **Attempts**: `plannerMaxAttempts` (2 by default). On each attempt it builds
  the prompt, runs the agent, and extracts and validates the JSON; if that fails,
  it retries with the error as feedback.
- **Prompt**: in Spanish; includes the goal, current plan, conversation,
  already completed tasks (do not repeat), failed tasks, the supervisor's
  reason, instructions and (if applicable) the feedback from the previous
  attempt. It ends with an exact JSON example and the rules (unique IDs,
  existing dependencies, no cycles, at least one task without dependencies).
- **JSON extraction**: prefers a ``` ```json ... ``` ``` block; otherwise it cuts
  from the first `{` to the last `}`.
- **Zod validation** (`generatedPlanSchema`): `summary` (string, default `""`) +
  `tasks` (array, minimum 1). Each task: `id`, `title`, `description` (min. 1),
  `type` (enum), `complexity` (enum), `dependsOn` (string[], default `[]`),
  `acceptanceCriteria` (string[], default `[]`).
- **Structural validation** (`validateGeneratedPlan`): non-empty, no duplicate
  IDs, no nonexistent dependencies, no cycles, no manual-verification criteria
  (real browser, visual inspection) and **no absolute filesystem paths**
  (`/Users/...`, `C:\...`, `~/...`). Criteria must use paths relative to the
  repository root (`package.json`, `src/index.ts`): the task runs in an isolated
  worktree and an absolute path would point outside of it.
- If the attempts run out, it throws
  `El planner no generó un plan válido tras N intentos: <detalle>.`

**PlanContext**: `previousPlan?`, `completedTaskIds?`, `failedTaskIds?`,
`supervisorReason?`, `instructions?`, `conversation?`.

## 11. Scheduler (DAG execution)

`src/scheduler/scheduler.ts` — `runPlan(tasks, options)`.

### Validation (`validation.ts`)

`validatePlan(tasks)` throws if:

1. There are **duplicate IDs**: `El plan contiene IDs duplicados: ...`
2. There are **nonexistent dependencies**: `El plan tiene dependencias inexistentes: ...`
3. There are **cycles** (DFS): `El plan contiene una dependencia circular: A → B → A`

### Status recalculation (`dependencies.ts`)

`updateTaskStatuses(tasks)`:

- **Preserved**: `done`, `failed`, `running`.
- **Blocked by integration** (`status: "blocked"` + `integrationError`) is
  **sticky** (not recalculated).
- No dependencies → `ready`.
- If any dependency is `failed` → `blocked` with
  `bloqueada por <ids> (failed)`.
- If all dependencies are `done` → `ready`.
- Otherwise → `blocked` with `esperando a <pending ids>`.
- `interrupted` is **not** preserved: it is recalculated (normally to `ready`).

### Execution

`runPlan` is a **sliding pool**: it dispatches continuously, without waiting for
the group of in-flight tasks to finish.

1. Resolves `concurrency` (default 2; integer ≥ 1 or it throws) and
   `maxConcurrency` (ceiling; if undefined, concurrency is fixed).
2. `validatePlan`; clones tasks; `updateTaskStatuses`; `onUpdate`.
3. Loop:
   - If `shouldPause()` or `signal.aborted`, it stops dispatching (but waits for
     in-flight tasks before returning `paused` / `cancelled`).
   - Fills free slots: takes from `getReadyTasks()` those not already in flight
     and dispatches until reaching `concurrency`. Each one is marked `running`
     and `onUpdate` is called.
   - If anything is in flight, `Promise.race` over the pending tasks: it resumes
     as soon as **the first one** finishes, which is when a slot frees up.
   - When a task finishes: its result is folded into `current`, concurrency is
     adjusted, dependencies are recalculated (`updateTaskStatuses`) and
     `onUpdate` is called. Recalculating here — and not at the end of a batch —
     is what lets its dependents start immediately.
   - With nothing in flight and no `ready` tasks: **`failed`** if there are
     failures, otherwise **`blocked`**. All `done` → **`completed`**.
   - **Concurrency adjustment** (`nextConcurrency`), for each task that
     finishes: if it exhausted its agents due to availability
     (`classifyAvailability` unavailable) it is halved (min. 1); if it ended
     `done` it goes up by one up to `maxConcurrency`. Each change is emitted via
     `onConcurrencyChange`. If concurrency drops while tasks are still in
     flight, nothing new is dispatched until the pool falls back below the
     ceiling.
4. `executeTask` defaults to `runTask`. A task that resolves to an unexpected
   status (neither `done`/`failed`/`blocked`) is forced to `failed`.

**Why not batches**: the previous version did a `Promise.all` over
`ready.slice(0, concurrency)`. One slow task left the other slots idle until it
finished, and its dependents did not start until the end of the batch. With
tasks ranging from seconds to minutes, that dead time was most of the plan's
delay.

### Result

`PlanResult { status, tasks, startedAt, finishedAt, failedTaskIds?, blockedTaskIds? }`
with `status ∈ completed | failed | blocked | paused | cancelled`.

## 12. Task execution (retries + fallback + worktrees)

`src/tasks/runner.ts` — `runTask(task, options)`.

**Precondition**: the task must be `ready`; otherwise it throws
`La tarea <id> no se puede ejecutar (estado actual: <x>). Se esperaba "ready".`

**Execution loop**:

```
for each candidate in agentHealth.order(getFallbackChain(task)):  // 3 candidates
  for attempt in 0..maxRetriesPerAgent:              // 2 attempts per candidate
    1. create a clean worktree from baseRef
    2. run the agent with cwd = worktree
    3. commit the result on the attempt's branch
    4. remove the worktree (deleting the branch if there was no commit)
    on success -> task done with executedBy, output, resultCommit (+ recordSuccess)
    if the provider is unavailable (quota/rate limit/auth/CLI) -> next candidate
      (if it is a limit -> agentHealth.markLimited: goes last in subsequent tasks)
    on retryable failure with attempts left -> retry the same candidate
    on non-retryable failure or attempts exhausted -> next candidate
if ALL candidates fell over on a limit (rate/usage) -> wait and walk the chain
  again up to limitRetry.maxLimitRetries (provider's retry after or backoff)
if candidates run out -> task failed
```

The orchestration roles (planner, supervisor, grill, instructions) use the same
mechanism via `runRoleAgent` (`src/agents/role.ts`), without worktrees. The
reviewer is the exception: it runs with `cwd` in the attempt's worktree (inside
`onWorkspaceSuccess`, before it is deleted) so it inspects the real files
instead of the main copy, which by design does not contain the changes.

Details:

- `prompt` = the task's base prompt (+ `extraPrompt` with review feedback).
- `maxRetriesPerAgent` defaults to **1** (=> up to 2 attempts per agent).
- Isolation guard: if the agent's `cwd` equals the repo root, it throws
  `Aislamiento inválido...`.
- Each attempt records a `TaskAttempt` (agent, number, dates, status, error,
  workspace, branch, baseRef, commitSha).
- Each attempt by the same agent starts from a **clean** worktree from the same
  starting point: partial artifacts from a failed attempt do **not** contaminate
  the next one.
- **Fix cycles**: `runTask` accepts `startRef`. In the first cycle the worktree
  starts from `baseRef`; in review/fix cycles it starts from the previous
  `resultCommit`, so the agent **continues** the work instead of redoing it. When
  finished, `squash(workspace, baseRef, msg)` reapplies the final tree as a
  single commit on top of `baseRef` (with `git reset --soft` + `commit`), so the
  task's cherry-pick remains a single commit. If the fix introduces no changes,
  the previous commit is kept.
- If the `AbortSignal` is aborted → `failed` with `Ejecución cancelada por el usuario.`
- A `coding` task that produces no commit (first attempt, no fix cycle) is
  considered failed: an agent that cannot write to the worktree (DeepSeek
  without a harness, or a CLI without permission) creates no files, and without
  this guard the project would be marked `completed` without having created
  anything. The fallback chain then moves on to the next agent capable of
  editing (Claude, DeepSeek with a harness or Codex) or the task fails.

## 13. Reviewer and local checks

### Local checks (`src/checks/checks.ts`)

- `detectCheckScripts(dir)`: reads `package.json` and returns the intersection
  of `["typecheck", "build", "test"]` with the declared scripts (in that order).
  If there is no `package.json` or parsing fails → `[]`.
- `ensureDependencies(dir)`: if `node_modules` is missing, it tries to seed it
  from the store (see below) and, if there is no entry, detects the package
  manager (`detectPackageManager`) and runs its `install`. Checks run in the
  agent's worktree (not a separate one), so if the agent already installed the
  dependencies they are reused. It is best-effort: if it fails, a warning is
  issued and the checks are run anyway.
- `runInstallCheck(dir)`: seeds from the store and runs the manager's `install`
  **even if `node_modules` already exists** ("installs without errors" is a
  common acceptance criterion and can only be verified by running it). If it
  finishes successfully, it saves the tree in the store. It runs with `audit`,
  `fund` and the progress bar disabled; it does **not** force `prefer-offline`,
  which resolved against stale metadata and failed with `ETARGET` on recent
  dependencies.

### Dependency store (`src/checks/deps-store.ts`)

Each attempt of each task runs in a freshly created worktree, which is born
without `node_modules` (it is not committed). Installing from scratch there was
the slowest part of the cycle: the agent paid for it at startup and again in the
install check.

- **Key** (`dependencyKey`): hash of the package manager plus the contents of the
  first lockfile that exists (`pnpm-lock.yaml` → `yarn.lock` →
  `package-lock.json`). Without a lockfile, a hash of the `package.json` fields
  that decide what gets installed (`dependencies`, `devDependencies`,
  `optionalDependencies`, `peerDependencies`, `overrides`, `resolutions`,
  `packageManager`). The name, version and scripts are not part of it: two tasks
  of the same project share an entry. Without `package.json` → `undefined` and
  nothing is done.
- **Location**: `~/.cache/mrrobot/deps/<key>`, configurable with
  `MRROBOT_DEPS_CACHE`.
- `primeDependencies(dir)`: if `dir` has no `node_modules` and there is an entry
  for its key, it copies it with hard links (`cp -al`, falling back to `cp -a`;
  `robocopy` on Windows). It is written to a temporary directory inside the
  worktree and renamed, to avoid leaving half-built trees. Returns `hit`, `miss`,
  `present` or `skip`. **It is called from `runTask` before starting the agent**,
  so the agent does not install either.
- `saveDependencies(dir)`: saves `dir`'s `node_modules` if there is no entry yet
  for its key. It writes separately and renames (atomic), so two tasks saving at
  the same time do not corrupt the store.
- None of this throws: on any failure it falls back to a normal install.

Measured on a Next.js project with a lockfile, the dependency cost per task drops
from ~6.7 s to ~0.5 s.

- `runProjectChecks(dir, scripts)`: runs `npm run <script>` with `execFile`;
  never rejects; truncates stdout/stderr to 4000 characters. `build` and `test`
  are kept **in order** (test may need the build); the rest (`typecheck`,
  `lint`…) run **in parallel** with that chain. Results are returned in the
  original order.
- `DEFAULT_CHECK_SCRIPTS = ["typecheck", "build", "test"]`.

### LLM reviewer (`src/reviewer/reviewer.ts`)

- `reviewTask(task, context, deps)`: agent chosen by the task's complexity,
  restricted to the allowed ones and with fallback (`runRoleAgent`).
- `shouldSkipReview(task, checks)`: skips the LLM review only if the task is
  `low`, has no `acceptanceCriteria`, and there are checks that exist and pass.
  If there are no checks, the review remains the only validation. With any failed
  check there is no LLM review either: it is rejected directly.
- **Bounded cost**: for checks that pass only "OK" is sent; the diff is cut at
  `MAX_REVIEW_DIFF_CHARS` and the agent's output to its last
  `MAX_REVIEW_OUTPUT_CHARS` (the reviewer can open the worktree's files).
- A non-JSON response is retried once; if it still isn't JSON, or no reviewer is
  available, the result carries `unavailable: true` and the task fails without
  spending fix cycles.
- **Context**: `diff` (of the commit), `output` (of the agent), `checks` (local
  results), `acceptanceCriteria` (of the task) and `repoRoot` (to re-anchor
  criteria with absolute paths inside the repo to relative ones).
- **`cwd`**: `ReviewerDeps.cwd` forces the reviewer's inspection directory over
  the one the executor brings (which points at the main repo). The review/fix
  cycle sets it to the attempt's worktree.
- Strict prompt: `approved` must be `false` if any criterion is not met or any
  check fails.
- Output validated with Zod: `{ approved, summary, issues[], suggestedFixes? }`.
- **Fail-safe**: if the response is not parseable or the agent fails, it returns
  `approved: false` (never throws).

### Review/fix cycle (in `projects/service.ts`)

For each task, up to `maxReviewFixCycles + 1` iterations (default **3**):

1. Runs the task (`runTask`) with the accumulated feedback. From the second cycle
   on it passes `startRef = ` the previous `resultCommit`: the agent continues on
   its own work and the result is flattened into one commit on top of the base.
2. Runs the local checks in the agent's worktree, before removing it
   (`onWorkspaceSuccess` callback), reusing its `node_modules` if present.
3. Gets the commit's `diff`.
4. Calls the reviewer.
5. **Approved** only if `review.approved === true` **AND** all checks pass.
6. Otherwise: emits `task.review_failed`, builds the feedback
   (`buildFixFeedback`: issues + suggestions + failed checks) and repeats.
7. If the cycles run out: task `failed` with
   `review no aprobado tras N ciclos`.

## 14. Supervisor and replanning

`src/supervisor/supervisor.ts` — `superviseProject(project, context, deps)`.

- Agent chosen by complexity, restricted to the allowed ones, with fallback.
- Decides between: `continue`, `replan` (with `instructions?`), `pause`, `fail`.
- The prompt includes the goal, a summary of task statuses, the project status,
  the trigger, the number of failures and a warning about integration conflicts.
- **Fail-safe**: if the decision is not parseable or the agent fails →
  `continue` (`supervisor no disponible: ...`). **Never throws.**

### Replanning (`mergeReplan`)

When the supervisor decides `replan`:

1. The planner receives the goal, the completed/failed tasks, the supervisor's
   reason and (optionally) instructions.
2. `mergeReplan(existing, plan)`:
   - Keeps `done` tasks as they are.
   - Resets the other existing tasks to `todo` (keeping their fields).
   - Adds only the **new** tasks from the plan (if an ID already exists, the
     existing one wins).
   - Validates the resulting DAG.
3. `supervisor.replan` is emitted and execution continues with the next round.

## 15. Project orchestration

`src/projects/service.ts` is the core. Constant `MAX_SUPERVISOR_ROUNDS = 3`.

### Main cycle (`runProject`)

1. Loads the project and **recovers `running` tasks** to `interrupted`
   (`recoverInterrupted`).
2. Status → `running`, `startedAt`, emits `project.started`.
3. Repeats for up to **3 rounds**:
   - `runProjectRound`: runs the entire DAG.
   - If `completed` → `finalizeProjectRun`.
   - If `paused` → status `paused`, emits `project.paused`.
   - If `cancelled` → status `cancelled`, emits `project.cancelled`.
   - Counts failures and detects integration conflicts.
   - Calls the **supervisor** and persists its decision.
   - `replan` → replans and continues with another round.
   - `pause` → `paused`; `fail` → `failed`.
   - `blocked` → exits the loop.
4. `finalizeProjectRun`.

### Finalization (`finalizeProjectRun`)

- If **all** tasks are `done`:
  - `finalizeProject` integrates the commits into
    `agent/project-<id>-final` (cherry-pick).
  - If it integrates: `completed`, stores `resultBranch`/`resultCommit`, emits
    `project.completed`.
  - If `remoteUrl` and `GITHUB_TOKEN`: tries to push and emits `project.pushed`
    or `project.push_failed`.
  - If integration fails: `failed` + `git.conflict`.
- If **not** all are `done`: `failed` if any is `failed`, otherwise `blocked`.

### Other service operations

| Function | Effect |
|---|---|
| `createProject` | Plans and creates the project in `ready`. |
| `createProjectDraft` | Creates the project in `draft` **without** planning (used by the API). |
| `generatePlan` | `planning` → `ready`; rejects if `running`/`completed`. |
| `pauseProject` | → `paused`, emits `project.paused`. |
| `cancelProject` | → `cancelled`, emits `project.cancelled`. |
| `resumeProject` | Recovers interrupted tasks, → `running`, emits `project.resumed`, and runs. |
| `deleteProject` | Deletes the project from storage (does not touch disk). |
| `buildProjectResult` | Builds `ProjectResult` only if `completed` with branch/commit/dates. |

### LangGraph graph (`src/graph/graph.ts`)

Alternative engine with `StateGraph` + `MemorySaver` and `MAX_GRAPH_ROUNDS = 6`:

```text
START → plan → run → supervise ─┬─ replan → plan
                                 ├─ continue → run
                                 ├─ pause/fail → END
                                 └─ finalize → END
```

- `plan` node: only replans if the previous decision is `replan`; otherwise it
  passes the project through unchanged.
- `run` node: runs one round; increments `rounds`.
- `supervise` node: if all tasks are `done`, it decides `continue` without
  calling the supervisor.
- `finalize` node: integrates the result.

## 16. Workspace and Git

`src/workspace/manager.ts` (constant `WORKTREES_DIR = ".worktrees"`).

### Naming conventions

| Purpose | Branch | Worktree |
|---|---|---|
| Task attempt | `agent/<taskId>-attempt-<N>` | `.worktrees/<taskId>-attempt-<N>` |
| Dependency integration | `integration/<taskId>` | `.worktrees/integration-<taskId>` |
| Project's final branch | `agent/project-<id>-final` | `.worktrees/project-<id>-final` |

IDs are **sanitized** (`sanitizeTaskId`): invalid characters → `-`, `..` is
collapsed, leading/trailing `-`/`.` are stripped; if nothing is left → `task`.

### Operations

- `getRepoRoot` / `resolveBaseRef`: `git rev-parse` (`--show-toplevel`, `HEAD`).
  The root is **memoized per path** for the lifetime of the process (it is
  queried many times per task and attempt); a failure is not cached.
  `resolveBaseRef` reuses the cached root and only runs `rev-parse HEAD`.
- `prepareProjectRepo(repoPath, remoteUrl?)`: creates the folder if it does not
  exist, runs `git init` if it is not a repo, makes an empty initial commit if
  there is no HEAD (`chore: initial commit`, identity `MrRobot <mrrobot@localhost>`),
  configures `origin` and verifies the remote, and adds `.worktrees/` to
  `.git/info/exclude`.
- `create` / `commit` / `remove` / `diff`: worktree lifecycle. `commit` returns
  `undefined` if there are no changes (empty `git status --porcelain`).
- `integrateDependencies(taskId, commits, baseRef)`: no commits → no-op
  (`ref = baseRef`); if there are some, it creates `integration/<taskId>` and
  `git cherry-pick`s each dependency commit. On success it **keeps** the branch;
  on conflict it **deletes** it and returns an `IntegrationError`.
- `finalizeProject(projectId, commits, baseRef)`: cherry-picks all commits into
  `agent/project-<id>-final`.
- `push(branchName)`: `git push --set-upstream origin <branch>` with credentials
  from `GITHUB_TOKEN` if applicable.

### Conflicts

- A conflict is detected on **any** `cherry-pick` failure (or failure to create
  the integration worktree).
- Conflicting files are obtained with
  `git diff --name-only --diff-filter=U`.
- The task is left `blocked` with `integrationError` (`type: "git_conflict"`),
  `blockedReason` and `files`.
- **The main repo is never touched**: all operations happen in the worktree. On
  conflict, `cherry-pick --abort` is run, the worktree is removed and the branch
  is deleted.

### GitHub

- `GITHUB_TOKEN` enables non-interactive HTTPS authentication via
  `credential.helper`.
- `GIT_TERMINAL_PROMPT=0` is used to avoid interactive prompts.
- When creating a project with `remoteUrl` + token, it is validated with
  `git ls-remote`.
- On completion, if there is a `remoteUrl`, the final branch is pushed.

## 18. Per-project chats

`src/chats/service.ts`. A project can have several chats (independent threads),
available in every status except `running`.

### Creating a chat

`createChat(projectId, {title?, message?})`:

- Rejects if the project is `running`.
- `seq = max(existing seq) + 1`; title derived from the message or `Chat <seq>`.
- Emits `chat.created`.
- If there is a `message`, it is sent immediately (same flow as sending a message).

### Sending a message (planner flow)

1. Rejects if the project is `running`; validates the chat and the content.
2. Persists the `user` message and emits `chat.message`.
3. Builds the planner context: project goal, the chat's current plan,
   conversation and instructions (= the message).
4. The planner returns a plan.
5. The plan's IDs are **prefixed per chat** (`C1-TASK-001`, `C2-TASK-001`, …) so
   they do not collide across chats; tasks are associated via `task.chatId`.
6. `mergeChatTasks`: keeps the chat's `done` tasks, keeps other chats' tasks
   intact and replaces the rest with the new plan.
7. **Reactivation**: if the project was `draft`/`completed`/`failed`/
   `cancelled` and the chat adds pending tasks, it goes back to `ready` (clearing
   `finishedAt`, `resultBranch`, `resultCommit`).
8. Saves the `assistant` message (summary + IDs) and emits `chat.message` and
   `plan.updated`.
9. **Errors**: if the planner fails, it saves an `assistant` message with the
   error (`No pude generar el plan: ...`) and does **not** throw.

Deleting a chat removes its tasks and messages (emits `chat.deleted`).

In the UI, chats appear as a **Chats** tab and in the sidebar (with a `+` button
to create a new one); clicking one opens `/projects/:id?chat=:chatId`.

## 19. Preview (development server)

`src/preview/preview.ts` — `PreviewManager`.

## 20. Importing projects

`src/projects/import.ts` — `importCompletedProject(input, deps)`.

Rebuilds a MrRobot project from an already existing **final branch**
(`agent/project-*-final`).

1. Resolves the repo root.
2. Uses the given branch or the first final one (sorted by commit date).
3. Gets `resultCommit` and derives the `id` from the branch name.
4. Rejects if a project with that id already exists.
5. Walks the log (`git log --reverse`) and **rebuilds the tasks** from commits
   whose subject is `agent(<taskId>): <title>` (all `done`, type `coding`,
   complexity `low`).
6. Creates the project in `completed` status with `resultBranch`/`resultCommit`.
7. Emits `project.created`, `plan.generated`, one `task.completed` per task and
   `project.completed`.

`listFinalBranches(repoPath)`: lists `refs/heads/agent/project-*-final` branches
sorted by commit date, descending.

  `failed`/`blocked` tasks; asks the task's agent, which answers `proceed`
  (changes the approach) or `ask` (asks the user for clarification), and records
  the exchange as `task.instruction` / `task.instruction_reply`.
- **Config editing**: only in `draft`/`ready`/`paused`.
- **Pause**: cooperative at batch level (in-flight tasks finish).
- **Cancel**: aborts in-flight CLI processes (`AbortSignal`); DeepSeek stops at
  the end of the batch.
- **Delete**: does not allow deleting a running project; does not touch disk.

### Runtime (`src/api/runtime.ts`)

- Creates storage (PGlite or memory), workspace (Git or mock) and config.
- Keeps `activeRuns`, `pauseFlags` and `cancelControllers` per project.
- Wraps the storage in a `Proxy` that **emits every event** to the bus (SSE).
- `depsFor(projectId)` uses a workspace bound to `project.repoPath` if it exists.
- `info()` exposes `repoRoot`, `baseRef`, `mock`, agent availability and config.
- `shutdown()` stops previews and closes storage.

### Serialization (`src/api/serialize.ts`)

Converts domain → wire: `serializeProject`, `serializeSummary`,
`serializeTask`, `serializeEvent`, `serializeReview`, `serializeSupervisorRun`,
`serializeChatSummary/Detail`, `serializeAgent`, `describeAgent`.
`computeStats` computes `ProjectStats` (progress = `done/total`; `activeAgents` =
running; `blocked` + `interrupted` count as `blocked`).

## 22. Real time (SSE)

- Endpoint: `GET /api/projects/:id/stream` (`text/event-stream`).
- On connect it emits `{type:"connected", projectId}`.
- Every event-log event is emitted as an SSE message; the runtime filters by
  `projectId`.
- Heartbeat `: ping` every 15 s.
- The UI (`useProject`) subscribes and, on every message, does a **debounced
  (60 ms) reload** of project + events + reviews + supervisor + chats.
- The backend is the **single source of truth**: an `F5` rebuilds state from
  persistence.

## 25. State machines

### Project status

```text
draft → planning → ready → running → paused | blocked | completed | failed | cancelled
```

- **Creation**: `ready` (with a plan) or `draft` (without a plan, via API/UI).
- **`planning`**: while the planner generates the DAG.
- **`ready`**: plan ready and editable; execution can be launched.
- **`running`**: executing rounds.
- **`paused`**: cooperative pause; resumable.
- **`blocked`**: no runnable tasks (dependencies/conflicts).
- **`completed`**: all tasks `done` and integrated into the final branch.
- **`failed`**: there are failed tasks or the final integration failed.
- **`cancelled`**: cancelled by the user.

Relevant transitions:

| From | Action | To |
|---|---|---|
| `draft`/`ready`/`paused`/`failed`/`blocked`/`cancelled` | `generatePlan` | `planning` → `ready` |
| `ready` | `run` | `running` |
| `running` | `pause` | `paused` |
| `paused` | `resume` | `running` |
| `running`/`paused` | `cancel` | `cancelled` |
| `running` | ends with no failures | `completed` |
| `running` | ends with failures | `failed` |
| `running` | ends with no ready tasks and no failures | `blocked` |
| `draft`/`completed`/`failed`/`cancelled` | chat with pending tasks | `ready` |

### Task status

```text
todo → blocked → ready → running → done | failed
                     ↑         ↓
                  interrupted (after a crash)
```

- **`todo`**: just created.
- **`blocked`**: depends on tasks that are not `done`, or has an integration
  conflict (sticky).
- **`ready`**: dependencies satisfied, runnable.
- **`running`**: executing.
- **`interrupted`**: was left `running` after a crash; recovered to `ready`.
- **`done`**: executed and approved (review + checks).
- **`failed`**: failed after exhausting retries/fallbacks or review cycles.

## 27. Mock mode

With `MRROBOT_MOCK=1`, agents, planner, reviewer, supervisor, worktrees and
storage (in memory) are simulated, deterministically and without spending tokens.

Scenarios (`MRROBOT_MOCK_SCENARIO`):

| Scenario | Behavior |
|---|---|
| `success` (default) | The planner returns the base plan; workers complete; the reviewer approves; the supervisor continues. The project **completes**. |
| `replan` | The first worker attempts fail to force a replan; the planner returns an expanded plan (adds a `TASK-005` CI task) on its second call; the supervisor asks for `replan`. |
| `fail` | All workers fail; the supervisor decides `fail`. The project **fails**. |

- Base plan: 4 tasks (`TASK-001` Scaffold, `TASK-002` Implement `sum`,
  `TASK-003` Tests, `TASK-004` README).
- `MRROBOT_MOCK_DELAY_MS` adds artificial latency per agent execution.

## 28. All possible flows

### 28.1 Main flow (UI, from zero to completed)

1. **Create**: `/projects/new` → name + goal (+ folder/remote/advanced) →
   `POST /api/projects` (draft) → `POST /api/projects/:id/plan` → navigate.
2. **Plan**: status `planning`; the planner generates and validates the DAG →
   `ready`. The UI shows it as List/Graph.
3. **Review/edit** (optional, `ready` only): add/edit/delete tasks
   (`POST/PATCH/DELETE .../tasks`), adjust config (`PATCH .../config`), or
   iterate via chat.
4. **Run**: `Start project` → confirmation → `POST .../run` → `running`.
5. **Monitor**: board, graph, activity and chats live (SSE);
   `Pause`/`Resume`/`Cancel` depending on status; supervisor banners.
6. **Finish**: `completed` (or `failed`/`blocked`) with final branch and commit;
   `ResultView` with the agents used and issues.
7. **Preview** (optional): `POST/GET/DELETE .../preview` to start the result's
   dev server.
8. **Integrate** (manual, outside the engine): the user decides whether to merge
   `agent/project-<id>-final` into `main`.

### 28.2 Flow with failed review and correction

1. A worker completes a task, but the reviewer or a check rejects it.
2. `task.review_failed` is emitted; the engine retries with the review feedback.
3. Up to `maxReviewFixCycles + 1` cycles.
4. If approved → `task.completed`; otherwise → `task.failed`.

### 28.3 Agent fallback flow

1. The preferred agent fails (transient error) → the same agent is retried
   (`maxRetriesPerAgent`). If the provider is unavailable (quota, rate limit,
   auth or missing CLI) it jumps straight to the next one.
2. If it keeps failing or the error is non-retryable (e.g. quota/`401`) → jumps
   to the next agent in the chain.
3. Each attempt starts from a clean worktree.
4. If **all** candidates fall over on a limit (rate/usage) → it waits (retry
   after or backoff) and walks the chain again up to `limitRetry.maxLimitRetries`.
5. An agent that falls over on a limit is quarantined (`AgentHealth`) and moves to
   the end of the chain in subsequent tasks and roles until it recovers, so the
   engine does not start over with the one that failed.
6. If the candidates (or the limit retries) run out → `task.failed`.

### 28.4 Replanning flow

1. A round ends with failures.
2. The supervisor decides `replan` (with optional instructions).
3. The planner generates a new plan with context about completed/failed tasks.
4. `mergeReplan` keeps the `done` ones, resets the rest and adds what is new.
5. The next round continues (up to 3 in `service`, 6 in the graph).

### 28.5 Integration conflict flow

1. A task depends on commits from others.
2. `integrateDependencies` cherry-picks and there is a conflict.
3. `git.conflict` is emitted; the task is left `blocked` with `integrationError`
   and `files`.
4. The supervisor may replan; the main repo remains intact.

### 28.6 Pause/resume flow

1. `Pause` during `running` sets a flag; the scheduler finishes the current batch
   and launches no new tasks → `paused`.
2. `Resume` recovers `interrupted` tasks to `ready` and continues from the
   persisted state.

### 28.7 Cancellation flow

1. `Cancel` triggers the `AbortController`; in-flight CLI processes are killed.
2. DeepSeek (HTTP) stops at the end of the batch.
3. Status → `cancelled`.

### 28.8 Crash / recovery flow

1. If the process dies with `running` tasks, on resume they are marked
   `interrupted` (`recoverInterrupted`).
2. The scheduler recalculates them (normally to `ready`) and they are retried.
3. An `F5` in the UI rebuilds the state from persistence.

### 28.9 Chat flow (iterating on the plan)

1. Create a chat (Chats tab or the sidebar `+`).
2. Send a natural-language message.
3. The planner generates a plan; IDs are prefixed per chat; tasks are merged
   (keeping the `done` ones and those of other chats).
4. If the project was finished, it goes back to `ready` so it can be relaunched.
5. Deleting the chat removes its tasks and messages.

### 28.10 Import flow

1. Dashboard → `Import` → choose the folder and final branch
   (`agent/project-*-final`).
2. `POST /api/projects/import`.
3. Tasks are rebuilt from the commits and the project is left `completed`.

### 28.11 Preview flow

1. `completed` project → `ResultView` → `Abrir preview` (Open preview).
2. A worktree of the final commit is created, dependencies are installed (if
   needed) and the dev server is started.
3. The UI shows the URL and log; `Detener` (Stop) shuts it down.

### 28.12 CLI flow

1. `create` → plans and creates.
2. `plan`/`tasks` → inspect.
3. `run` → execute (blocking, prints the status).
4. `status` → view the status.
5. `pause`/`resume`/`delete`.

### 28.13 Flow with push to GitHub

1. Project with `remoteUrl` and `GITHUB_TOKEN` defined.
2. On creation: access is validated (`git ls-remote`).
3. On completion: `agent/project-<id>-final` is pushed to the remote.
4. `project.pushed` is emitted (or `project.push_failed` without changing the
   status).

## 29. Errors and HTTP codes

The API maps domain errors to codes based on the message (the messages
themselves are emitted by the engine in Spanish, so they are quoted verbatim
here):

- `ProjectNotFoundError` → **404**.
- Conflict messages (`/ya se está|Solo se puede|No se puede/`) → **409**.
- Bad-request messages (`/inválido|obligatorio|desconocido|debe ser|no vacío|no se enviaron|requiere|No se puede/`) → **400**.
- Anything else → **500**.

Notable messages:

| Message | Situation |
|---|---|
| `El objetivo del proyecto es obligatorio.` | Empty `goal`. |
| `No se puede generar el plan en estado X.` | Plan while `running`/`completed`. |
| `No se puede ejecutar en estado X. Genera y revisa el plan primero.` | Run without `ready`. |
| `El proyecto ya se está ejecutando.` | Concurrent run/resume. |
| `Solo se puede reanudar un proyecto pausado (estado actual: X).` | Invalid resume. |
| `No se puede borrar un proyecto en ejecución. Cancélalo primero.` | Delete while active. |
| `No se puede editar la configuración en estado X...` | Config outside `draft/ready/paused`. |
| `El plan no es editable en estado X...` | Plan edit outside `draft/ready`. |
| `No se pudo acceder al repositorio Git: ...` | Invalid repo. |
| `No se encontró ninguna rama final (agent/project-*-final) en el repositorio.` | Import with no branches. |
| `Ya existe un proyecto con id X.` | Duplicate import. |
| `Aislamiento inválido: el cwd del agente no puede ser la raíz del repositorio.` | Safety guard. |
| `[deepseek] falta DEEPSEEK_API_KEY (defínela en el archivo .env).` | Missing key. |
| `[lmstudio] no hay ningún modelo cargado en el servidor local (carga uno en LM Studio).` | Server reachable but no model loaded. |
| `[lmstudio] falló la ejecución: ...` | Local server down or wrong URL. |
| `CLI "<command>" no encontrado en el PATH.` | Missing CLI. |
| `Cuerpo de petición demasiado grande.` | Body > 1 MiB. |
| `JSON inválido en el cuerpo de la petición.` | Malformed body. |
| `El selector nativo de carpetas solo está disponible en macOS.` | `pick-folder` on another OS. |

## 31. Current limitations

- **Real Postgres**: only PGlite is implemented/verified; the `pg` adapter and
  Drizzle are pending.
- **LangGraph checkpointing**: uses `MemorySaver` (in memory). Resuming across
  processes relies on the persisted state + idempotent rounds; a Postgres
  checkpoint saver is missing.
- **E2E**: the tests use mocked (deterministic) agents; a full real smoke run has
  not been executed (Claude limited by subscription).
- **Final merge**: not automatic; the user decides whether to integrate the
  branch.
- **`concurrency`** is in-process (not distributed).
- **Pause**: cooperative at batch level; in-flight tasks finish.
- **Cancel**: cooperates with `AbortSignal` to kill CLI processes; DeepSeek
  (HTTP) stops at the end of the current batch.
- **Global activity**: the global page uses light polling (5 s); the real-time
  stream is per project (SSE).
- **DeepSeek** does not support `cwd`/`signal` (no worktree isolation or process
  cancellation).
